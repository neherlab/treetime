# Web2 runs the API router as WebAssembly in web workers

**Type**: Application architecture without a v0 counterpart.

**Status**: Accepted. The back end builds for `wasm32-unknown-emscripten`, and each run computes in a job worker of its own; the remaining work is in [Issues](#issues).

## Decision

The web2 app (`packages/app-web2`) renders the interface of `packages/app-ui` unchanged and reaches the back end through the same generated API client (`@neherlab/app-contracts/client`) as the web app and the desktop app. Only the `fetch` of the client differs:

- **Page**: `createPortFetch()` of `@neherlab/app-ui/port-fetch`, the fetch that the desktop renderer uses, sends each request through a message port, and transfers the buffers of upload bodies instead of copying them. `WorkerConnection` (`packages/app-web2/src/backend/connection.ts`) compiles the single-threaded WebAssembly module once, starts the back-end worker, and hands it the compiled module, its end of a message channel, the `jobs` value of the page, and the URL of the threaded module when the page can use threads
- **Back-end worker**: the worker creates an instance of the module from the compiled module (the `instantiateWasm` hook of Emscripten, `instantiateBackend()` in `packages/app-web2/src/backend/instantiate.ts`), and a rejection of the hook fails the start. `ExchangeServer` (`packages/app-web2/src/backend/serve.ts`) parses each port message, calls `Backend.fetch()` of the instance, and pulls the response head and the body chunks of the exchange, which it sends back with the chunk buffers transferred. An abort message aborts the exchange. The back-end worker keeps the run store and answers every request while runs compute, so the event stream of a run delivers its progress live
- **WebAssembly**: `Backend` (`packages/app-wasm/src/backend.rs`) holds the router of `api_router()`, the router of the public web server, so web2 has the routes and the validation of `treetime-server` and none of the routes of a local app. `Exchange` (`packages/app-wasm/src/exchange.rs`) drives one request through the router and gives its head and its body chunks on request, so a reader that stops pulling stops the body, and an abort ends a waiting read
- **One job worker per run**: a run computes in a dedicated worker that the back-end worker starts for this run, with its own instance of a module, so several runs may compute at the same time. The start request prepares the run (`StartedRun::prepare()` in `packages/app-backend/src/runs/lifecycle.rs`) and the run executor of the module (`JobExecutor` in `packages/app-wasm/src/jobs.rs`) queues a start order; Rust never calls into JavaScript. After the head of each response, the job host (`JobHost` in `packages/app-web2/src/backend/jobs.ts`) takes the queued orders (`Backend.takeJobOrders()`), starts a job worker (`packages/app-web2/src/job/worker.ts`), transfers the input files of the run into it, forwards each event of the job to the run's event log, receives the output files into the run's out folder, and completes the run. Each file transfer keeps at most 4 chunks without an acknowledgement. Stop terminates the job worker at once and records the run as cancelled. A panic or an out-of-memory abort in a job ends only that run, and the job's memory returns to the browser when its worker ends
- **Job states**: the job host is the one owner of the state of each job (`starting`, `inputs`, `computing`, `outputs`, `settled`). The first terminal result settles the job: `done` completes it, and a cancel, a crash, or a worker error fails it. Each worker start has an attempt number that every job message carries, and messages of an older attempt or of a settled job are ignored. An error before the worker reports `started`, or no `started` within 60 s, is a start failure
- **Threaded module with single-threaded fallback**: the job worker runs the threaded module, whose algorithms run in parallel on rayon threads (Emscripten pthreads). The URL parameter `jobs` of the page sets the number of threads of each run, as `-j/--jobs` does in the CLI: no parameter means 8, `jobs=1` selects the single-threaded module, and a value that is not a positive integer falls back to 8 with a warning in the console (`parseJobs()` in `packages/app-web2/src/backend/threads.ts`). The page uses threads only when it is cross-origin isolated, `SharedArrayBuffer` exists, and a shared `WebAssembly.Memory` with the 65536 pages of the module can be created (`chooseRunThreads()`), because iOS Safari and other browsers limit shared memory; otherwise every job runs the single-threaded module. After a start failure of a threaded job, the job host uses the single-threaded module for this job and every later job of the page. The back-end worker always runs the single-threaded module. With a fixed seed, the two modules give byte-identical outputs for `flu/h3n2/20` ancestral and timetree and `sc2/4500` timetree, except the paths that contain the run id (`alignment` and `input_tree` of `timetree.augur-node-data.json`, `partitions[].alignment` of every `*.gtr.json`), which differ between any two runs. A trial measured `sc2/4500` timetree in Chrome at 15.8 s with threads against 1 min 44 s single-threaded; [kb/issues/N-web2-supported-dataset-size-undocumented.md](../issues/N-web2-supported-dataset-size-undocumented.md) records the times by thread count
- **Runs in tab memory**: the run store lives in the in-memory file system of the back-end worker under `/treetime/runs`. The runs, their files, and the uploads stay in the tab until it reloads or closes, and the interface says so in its inputs section. web2 keeps no runs across page loads and has no run queue, no coordination between tabs, no service worker, and no offline copy
- **Failure text**: both workers pass `printErr` and `onAbort` to the module factory and listen for the global `error` event (`ErrorLines` in `packages/app-web2/src/backend/instantiate.ts`). The error lines of a failure are the last 20 lines of stderr (the default panic hook of Rust writes the panic message there, and an allocation failure its size), then the reason of `onAbort`, then the message of the `error` event, which covers a trap without stderr output. Emscripten forwards the stderr writes and the aborts of every thread to the main runtime thread, so the text of a panic on a rayon thread is kept too. A failed job becomes a run error with the last line as message and the earlier lines as causes; a crashed back-end worker shows the lines in the restart notice of the page
- **Stack safety**: the link flags `-sSTACK_OVERFLOW_CHECK=2` and `-Wl,--stack-first` stop the module with "stack overflow" on an overflow of the main stack or of a thread stack, and make an overflow that the check misses trap instead of overwriting static data and producing wrong outputs. They cost about 6 % (`sc2/4500` timetree, single-threaded `dist` module under Node: 17.7 s without, 18.7 s with)
- **Restart**: a back-end worker that fails before it is ready stops the back end for good (`restarts: false`), because a restart would fail the same way. A back-end worker that crashes later is replaced by a new worker with the same compiled module (`restarts: true`); requests in flight fail and later requests wait for the new worker, as in the desktop app
- **Example data**: every app takes example data from one generated index, `data/index.json` (`DataIndex` in `packages/app-backend/src/datasets.rs`), which lists every file that git tracks in `data/` except hidden files and folders, the datasets with their input files, the configs with the files they read, and the pipelines. The Vite plugin `exampleData()` (`packages/app-ui/build/example-data-vite.ts`) serves the listed files from the origin of web2 and of the hosted web app, and copies them into the build. The web apps upload a chosen example file into the run like a user file, and load a config with the uploaded paths through `replace_inputs` of the config check; the desktop app reads the files from its downloaded examples folder

## Target and platform

`app-wasm` is a binary crate for `wasm32-unknown-emscripten`. rustc links it through `emcc`, and `emcc` runs the wasm-bindgen CLI on the linked module (`-sWASM_BINDGEN`, experimental in wasm-bindgen 0.2.129). The result is one ES module, with the Emscripten runtime and the bindings, whose default export creates an instance, and the WebAssembly binary. The link settings of both builds are in `[target.wasm32-unknown-emscripten]` of `.cargo/config.toml`; every cargo call for the target adds the settings of its build with `--config`:

- **Single-threaded build** (`dev/cargo/wasm-st.toml`, `just build-wasm` into `packages/app-wasm/pkg/st/`): stable Rust and the single-threaded OpenBLAS
- **Threaded build** (`dev/cargo/wasm-mt.toml`, `just build-wasm-mt` into `packages/app-wasm/pkg/mt/`): the nightly of `dev/docker/files/wasm-threads-toolchain` rebuilds std with atomics (`-Zbuild-std=std,panic_abort`, `+atomics,+bulk-memory,+mutable-globals`), and the link uses `-pthread` and the threaded OpenBLAS. A new pthread worker starts only after its creator returns to the event loop, and rayon waits for every thread of its pool while it builds the pool, so the module starts a pool of `globalThis.treetimeJobs+2` pthread workers with the module (the rayon threads, the run thread, and one spare), and `-sPTHREAD_POOL_SIZE_STRICT=2` turns a request beyond the pool into an error instead of a hang. The job worker sets `globalThis.treetimeJobs` before it calls the module factory. The emitted JS starts its pthread workers from its own file name, so the build keeps the name `app_wasm.js`. Shared memory needs a cross-origin isolated page: the Vite servers of web2 send `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` (`server.headers` and `preview.headers` of `packages/app-web2/vite.config.ts`), and the page needs a secure context (HTTPS or `localhost`)

The package `@neherlab/app-wasm` exports `.` and `./app_wasm.wasm` (single-threaded) and `./threads` and `./threads/app_wasm.wasm` (threaded).

Emscripten provides the platform that the back end uses on the other targets:

- **C library**: OpenBLAS, LAPACK, and the compression libraries are compiled with `emcc` against the C library of Emscripten. The dev image installs a single-threaded OpenBLAS and a threaded one built with `-pthread` and `USE_LOCKING=1`, both for the `WASM128_GENERIC` target, with LAPACK from the C translation that ships with OpenBLAS, which [binarylandia/build_openblas](https://github.com/binarylandia/build_openblas) builds with `emcc` for the Emscripten version of the image (the entries `openblas-wasm32-unknown-emscripten` and `openblas-mt-wasm32-unknown-emscripten` of `.config/mise.image.toml`), so the linear algebra of web2 goes through the same BLAS and LAPACK interface as the CLI. Cargo links them through pkg-config: `/.cargo/config.toml` of the image names the single-threaded archive, and the threaded build passes `/.cargo/wasm-mt-env.toml`, which names the threaded one, because wasm-ld rejects the single-threaded archive in a threaded link. The functions of the C translation take no hidden string lengths and return `void`, as the `lapack-sys` declarations do; a call whose signature differs from its callee traps in WebAssembly. `xz` goes through `liblzma`, `zstd` through `zstd-sys`, both linked from the prebuilt WebAssembly archives of `binarylandia/staticbourg`, which contain no atomics and link into both builds
- **Files**: `std::fs` works on the in-memory file system of Emscripten, so the run store, the uploads, and the inputs and outputs of the commands run unchanged under `/treetime/runs`. Each module instance has its own file system, so a job worker writes the input files of its run at the same absolute paths as in the back end, checks their size and sha256 against the job, and sends back every file of the run's out folder
- **Clocks, process id, entropy**: `SystemTime`, `Instant`, `process::id()`, and `getrandom` (through `getentropy`) work, so a run without `--seed` draws and logs its seed as on the other targets
- **Memory**: each module instance grows its memory up to the 4 GiB of `wasm32` and has a main stack of 8 MiB

The back-end module has no threads and neither module has a tokio runtime or unwinding. The back end adapts to each with one `cfg(target_family = "wasm")` alternative or one run executor:

- **Threads**: the run executor (`RunExecutor` in `packages/app-backend/src/bridge/executor.rs`) decides where a run computes. Natively `ThreadExecutor` computes each run in a thread of its own; in web2 `JobExecutor` hands it to a job worker. Both platforms share the steps of a run: prepare, compute (`compute_run()`), and complete (`PreparedRun::complete()` and `fail()` in `packages/app-backend/src/runs/lifecycle.rs`). In the threaded job module, `Job::run()` (`packages/app-wasm/src/job.rs`) starts a run thread that builds the rayon pool with `jobs` threads and sends the events through a bounded channel to the job's main thread, the only thread that calls JavaScript; the futures executor of wasm-bindgen-futures waits there with `Atomics.waitAsync`. In the single-threaded module, `pthread_create` returns `ENOTSUP`, which Rust reports as `ErrorKind::Unsupported`, and rayon runs its work on the calling thread
- **tokio runtime**: the blocking work of a request runs in place, where natively it runs on the blocking pool of tokio (`run_blocking()` and `read_body_blocking()` in `packages/app-server/src/api/blocking.rs`). A request body is read in full before the blocking work. A run file or a run archive is sent in chunks of at most 1 MiB that the exchange pulls one at a time (`FileChunks` and `RunZipChunks` in `packages/app-backend/src/runs/files.rs`, used by `packages/app-server/src/api/download.rs`), so a download never holds a whole output in the linear memory, where one allocation of 2 GiB or more is impossible in `wasm32`. The request timeout (`packages/app-server/src/api/timeout.rs`) and the keep-alive of the event streams need tokio timers and exist only in the native builds; both protect sockets, and the worker has none
- **Blocking HTTP client**: the examples download of the desktop app (`packages/app-commands/src/examples_fetch.rs`) exists only in the native builds, because `reqwest` has no blocking client on WebAssembly targets
- **Unwinding**: wasm-bindgen does not support `panic = "unwind"` on this target, so a panic aborts the module. In a job worker the abort fails the run; in the back-end worker the page restarts the worker

## Types at each boundary

- **API requests and responses**: the generated types and zod schemas of the OpenAPI document, as in the other apps
- **JavaScript interface of the module**: wasm-bindgen generates it from the Rust signatures, and `emcc --emit-tsd` writes its declarations (`just gen wasm-types` writes `packages/app-wasm/pkg/app_wasm.d.ts`). Both builds declare the same exports, and `just build-wasm-mt` fails when the threaded declarations differ from the committed file. The workers take the types of `Backend`, `Exchange`, `ResponseHead`, `JobOrder`, `Job`, and the chunk reader from the declared `MainModule`. The interface uses only primitives, byte arrays, and exported classes, so it needs no serde derives (the workspace serializes with deser) and no hand-written declaration. The one string type is the event callback of `Job::run()`, `(event: string) => void`, because wasm-bindgen declares a typed `js_sys::Function` as `Function`. The one hand-written type is the set of options of the Emscripten runtime (`instantiateWasm`, `printErr`, `onAbort`), which the declarations type as `unknown`
- **Job channel**: Rust data passes between the two module instances as opaque JSON text: the job of a start order (`RunJob`), each event of a job (`JobEvent`), and the outcome of a job (`RunOutcome`), all deser types of `app-backend`. JavaScript never parses this text, and the receiving Rust code parses it with its deser types (`Job::new()`, `Backend.appendRunEvent()`, `Backend.completeRun()`). The job host reads only the run id, the order kind, and `inputPaths` of an order, the absolute paths of the input files of the job, which it transfers with `Backend.readRunInput()`. This is an exception to the rule that a value that reaches Rust is a Rust type with a derived schema that TypeScript validates with generated zod: the text goes from Rust to Rust, so a schema in TypeScript would check a copy of a Rust type that the Rust side already checks. `Backend.appendRunEvent()` rejects the start and terminal events, which only the back end emits, and the output paths are confined to the run's out folder
- **Message port messages** (`PortRequest`, `PortMessage`, `PortReply`): zod schemas declared once in `packages/app-ui/src/port.ts`. Every reply that the page receives and every message that the worker receives is parsed; a reply that breaks the protocol fails the open exchanges and later requests until a new port connects. These messages pass between two JavaScript contexts and carry the HTTP bytes as opaque data, so this is an exception to the same rule: in web2 the worker turns them into the primitive arguments of the generated interface, and in the desktop app a type test (`packages/app-desktop/src/__tests__/test_port_types.test.ts`) keeps the types that napi-rs generates for the addon within these schemas
- **Worker control messages** (start, ready, failed, crashed): zod schemas in `packages/app-web2/src/backend/protocol.ts`; they never reach Rust
- **Job worker messages**: zod schemas in `packages/app-web2/src/job/protocol.ts`, parsed by the receiving worker. Each message carries the attempt number, and Rust data crosses them only as the opaque JSON text of the job channel and as file chunks

## Reason

- One implementation of each API route, check, and command for the CLI, the web app, the desktop app, and web2; the interface needs no second client
- The transport of the desktop app already sends API requests through a message port to an in-process router, so web2 reuses its fetch and its restart behavior instead of a second protocol
- An RPC interface per operation (the approach of treeknit and Nextclade, with comlink and tsify) would need a second client in `app-ui` for every operation, and tsify needs serde derives on the types
- Emscripten supplies the C library, the file system, the clocks, and the entropy that the back end uses on the other targets, so web2 keeps OpenBLAS and the C codecs, and the run store and the commands run without a file system abstraction. `wasm32-unknown-unknown` has none of them: it would need a C library written by the project for OpenBLAS, a file system abstraction in the I/O layer of `treetime-utils` and the run store, and browser back ends for clocks and entropy. WASI targets have no wasm-bindgen support, so the interface of the module would be hand-written
- A job worker per run keeps the back-end worker free for requests and event streams while runs compute, lets Stop end a computation at once by terminating its worker, limits a panic or an out-of-memory abort to its run, and returns the memory of a run to the browser when its worker ends; the linear memory of one module instance never shrinks
- Threads make large runs several times faster, and the single-threaded module keeps web2 working where a page cannot be cross-origin isolated or shared memory fails
- Runs in tab memory need no storage that browsers may evict and no synchronization between the module instances. A store that outlives the page (IndexedDB through IDBFS, or the origin private file system through WasmFS) remains possible
- Example data from the origin of the page: a browser cannot download `examples.zip` from the GitHub release, which sends no CORS headers, and one generated index gives every app the same datasets and configs without a catalog route over a folder

## Implementation

- `packages/app-wasm/src/backend.rs`, `exchange.rs`, `chunks.rs`, `start.rs`: the WebAssembly back end
- `packages/app-wasm/src/jobs.rs`: the run executor of web2 and the job orders; `packages/app-wasm/src/job.rs`: the job of a job worker, with the run thread of the threaded module
- `packages/app-wasm/smoke.ts`: the smoke test of the built modules, which drives a back end and a job instance through the job protocol; `just test-wasm` runs it in Bun on the single-threaded module, `just test-wasm-mt` under Node on the threaded module with 2 and 8 threads, because Bun does not start the pthread workers of Emscripten; the test holds a timer while a threaded run computes, because Node does not stay alive for pthreads and a pending `Atomics.waitAsync`
- `packages/app-backend/src/runs/lifecycle.rs`: the prepare, compute, and complete steps of a run; `packages/app-backend/src/bridge/executor.rs`: `RunExecutor` and the native `ThreadExecutor`
- `packages/app-server/src/port.rs`: the requests and response headers of a message port exchange, shared with `packages/app-napi`
- `packages/app-server/src/api/blocking.rs`, `download.rs`, `timeout.rs`: the request work with and without a tokio runtime
- `packages/app-ui/src/port.ts`, `packages/app-ui/src/port-fetch.ts`: the message port messages and the fetch over a port
- `packages/app-ui/src/browser-backend.ts`: `BrowserBackend` and `useBrowserBackend()`, with which web2 downloads run files and archives through the generated client and an object URL, and shows that files and runs stay in the tab
- `packages/app-web2/src/backend/`: the worker connection, the back-end worker, the exchange server, the job host (`jobs.ts`), the choice of the module (`threads.ts`), and the error lines (`instantiate.ts`)
- `packages/app-web2/src/job/`: the job worker and its messages
- `packages/app-ui/build/content-security-policy-vite.ts`: `'wasm-unsafe-eval'` for the page of web2, which compiles the module
- `packages/app-ui/build/example-data-vite.ts`: the example data of the web apps from `data/index.json`; `dev/data-reindex` (`just data-reindex`) writes the index
- `dev/cargo/wasm-st.toml`, `dev/cargo/wasm-mt.toml`: the settings of the two builds; `dev/docker/files/wasm-threads-toolchain`: the nightly of the threaded build
- `.config/mise.image.toml`: Emscripten and the prebuilt OpenBLAS, liblzma, and libzstd archives of the dev image; `dev/docker/files/install-image-libraries` installs the archives and writes their pkg-config settings
