# App clients send the full command config

The HTTP server and the desktop back end accept, for each of the six app commands (`timetree`, `optimize`, `prune`, `ancestral`, `clock`, `mugration`), the same config object that `treetime <command> --config` reads. Every setting the CLI offers is available to the web and desktop apps, and all three clients run a command through one runner in `packages/app-commands`.

## Behavior

- **Request**: a run is created with a `CreateRunRequest`: the command name, the command's config as JSON with the keys and values of `packages/schemas/input-config-<command>.schema.json`, and `defer_start` to wait for uploads before the run starts. The start request may replace the command and the config given at creation. A run still waiting to start a day after its creation is removed the next time the server or the desktop back end starts. The server titles a new run `Run <local date and time of creation>`; the user renames it afterwards. The OpenAPI document `packages/app-contracts/openapi.json` embeds the config schemas as `<Command>Config` components, and the TypeScript types and zod schemas in `packages/app-contracts/src/generated/` are generated from it
- **Validation**: the config goes through the CLI config loader: defaults are filled in, the schema check rejects unknown keys (nested ones included), wrong types and invalid enum values, and the conversion to run arguments rejects missing required inputs. Error messages are the ones the CLI prints for the same config file
- **Config check**: `check-config` takes a command name and a config as YAML or JSON text. It returns either the config with every default filled in, the equivalent command line and YAML config, and the pre-run checks, or the error message, its cause chain, each problem with its location in the text, and the checks
- **Run events**: every command runs as a run, a record on disk (`run.json`) with its own folder. A run emits `started`, then `progress`, `log` and iteration events, then exactly one `terminal` event, and every event is appended to the run's `events.jsonl`. The terminal event is `ok` with the output files that exist after the run and their kinds, `error` with the message and its cause chain, `cancelled`, or `interrupted` for a run that was still running when the process stopped. A rejected config, a failed command and a panic all end in an `error` terminal event. Clients subscribe from an event offset, so a reloaded page or a reopened app resumes a running run's stream
- **Cancellation**: each running run owns its cancellation token, keyed by run id. `POST /api/runs/{id}/cancel` cancels a run on both transports. Closing an event stream does not cancel the run. Cancelling one run leaves other runs running
- **Errors**: every failed request answers an `ErrorResponse`: an error code (`not_found`, `upload_too_large`, `conflict`, `invalid_request`, `internal_error`), the message and its cause chain, with the HTTP status of the code (404, 413, 409, 400, 500). Malformed JSON bodies, path parameters and query parameters are `invalid_request`, not axum's plain-text rejections. A panic in an operation becomes an `internal_error`, so a panic does not stop the server or the desktop back end. The TypeScript client turns every error response into an `ApiError` with the status and the `ErrorResponse`
- **Paths on the server**: input paths must resolve, after following symbolic links, inside the data directory or the `inputs/` folder of a run (relative paths are resolved against the data directory). Browser files are uploaded into the run's own `inputs/` folder before the run starts. Output paths in the request are discarded; the server writes the outputs of a run to `<runs-dir>/<run-id>/out/`. Translation templates are expanded for each CDS and every expanded path is checked. The desktop back end reads any local path, because the desktop user owns the machine, and writes outputs into the run folder under `runs/` in the app's user-data directory

## HTTP API

- **One router**: `api_router(service, config)` in `packages/app-server/src/routes.rs` builds the axum `Router` of the REST API and its OpenAPI document. Each operation is one typed handler that calls one method of `AppService` (`packages/app-commands/src/bridge/service.rs`), the single implementation of every operation; blocking calls run on the blocking thread pool. The server and the desktop back end build the same router and differ only in the input policy of their `AppService`: the server confines input paths, the desktop back end does not
- **Server**: `create_router` adds the static files of the web app and CORS, and serves the router on TCP. The API is public: outside clients call the same REST paths and can generate their own SDKs from the document
- **Typed contract**: the handlers are registered through aide, which reads the request schema from each extractor type and the response schema from each return type, so the document cannot disagree with the handler signatures. Every request and response type derives `schemars::JsonSchema`, and aide generates the schemas with the project's draft 2020-12 settings. Each registration sets the `operationId` and the description, and every operation documents `ErrorResponse` as its `default` response. The adapters in `packages/app-server/src/api/` supply what axum and aide lack: extractors whose rejections are `ErrorResponse`, a typed SSE response that documents its event schema as `text/event-stream`, and file and archive responses
- **OpenAPI document**: `packages/app-contracts/openapi.json`, also served at `GET /api/openapi.json`. After aide builds it, `packages/app-server/src/openapi.rs` adds the per-command config schemas with their CLI annotations and the setting catalog, and turns every internally tagged enum (a `oneOf` of objects that share a constant tag property) into one `<Enum><Variant>` component per variant with a `discriminator` that maps each tag value to its component. Generation fails when a tagged union has no single tag property
- **Event streams**: server-sent events (SSE). `GET /api/runs/{id}/events` sends the events of a run; `GET /api/events` sends the changes to the runs (see App-wide events). Each SSE event carries its sequence number as `id`; a client resumes with the `from` query parameter or the `Last-Event-ID` header of a reconnect. A cancel, like every other message from the client, is an ordinary REST request
- **HTTP/2**: each open stream holds one connection, and browsers allow at most 6 HTTP/1.1 connections per host across all tabs. The API server speaks HTTP/1.1 without TLS, and browsers use HTTP/2 only over TLS, so a deployment puts a TLS-terminating reverse proxy that serves HTTP/2 in front of the server: portless (`https://treetime.localhost`) in development, for example nginx in production. `docs/dev/developer_guide.md` states the requirement

## App-wide events

- **Event**: `AppEvent` in `packages/app-commands/src/runs/app_events.rs` reports that a run was created or updated (started, ended, renamed, pinned or unpinned), with the new `RunSummary`. `RunManager` appends one event per change to a bounded in-memory log
- **Stale paths**: every event lists the REST paths whose answers the change made stale, computed in Rust next to the change. Each entry is `{ path, scope }`: `exact` covers the answers of the path itself for every query string and body, `subtree` also covers every path below it. A change to run `abc` lists `/api/runs` (exact), `/api/runs/abc` (subtree) and `/api/clade-in-runs` (exact). Clients invalidate what the server lists, so mutations carry no invalidation lists, and other tabs, other windows and outside clients stay consistent
- **Resync**: sequence numbers start at the process start time in microseconds, so a restarted server or utility process numbers its events above those of the previous one. When a client asks for an event the log no longer keeps, or for one above the head of the log, the stream starts with a `resync` event whose stale paths cover every run, then continues with new events

## TypeScript client

- **Generation**: `just gen` runs `@hey-api/openapi-ts` on the OpenAPI document and writes the types, the zod schemas and one SDK function per operation to `packages/app-contracts/src/generated/`. The zod schemas are `z.strictObject` for every closed object and `z.discriminatedUnion` for every tagged enum. The SDK validates each request before sending it and each response and each SSE event after receiving it. No TypeScript outside `src/generated/` holds an API path or an operation name, so adding an operation to the router needs no hand-written TypeScript
- **Client factory**: `createApiClient({ baseUrl, fetch })` in `packages/app-contracts/src/client.ts` configures the generated client with the `fetch` of the platform. It converts error responses to `ApiError` inside a wrapper around that `fetch`, because the generated SSE client does not run the client's response interceptors. An invalid SSE event rejects the stream
- **Resumable streams**: `resumableStream` in the same file opens a stream with `from` set to the last received sequence number plus 1 and reconnects with exponential backoff. It owns the reconnects because the retry counter of the generated SSE client never resets after a successful event, so a long-lived stream would stop after a fixed number of reconnects in total. A client error (status below 500) or an invalid event ends the stream
- **Web**: the web app uses `globalThis.fetch` with the page origin as base URL

## UI data layer

`packages/app-ui/src/api/` is the only way the UI reads and changes back-end data. It knows no operation and no path.

- **Keys from paths**: a query key is the request path split into segments, then the sorted query parameters, then the request body: `GET /api/runs/abc/results` has the key `["api", "runs", "abc", "results"]`. The key builder calls the SDK function with a capturing client and derives the path with the client's `buildUrl`, so keys follow the OpenAPI paths
- **Hooks**: `useApi(call, options)` reads, `useApiMutation(call, options)` changes; `call` is a closure over an SDK function, and the result type comes from it. A mutation that returns the changed resource can seed the cache entry of that resource
- **Invalidation**: `useAppEvents`, mounted once by `ApiProvider`, follows `GET /api/events` and invalidates every cached query whose key a stale path covers. There is no polling of the run list
- **Run events**: `useRunEvents(id)` is a TanStack `experimental_streamedQuery` over the run's event stream, keyed by the stream's path, with a reducer that derives the progress state. The stream ends with the terminal event
- **Save actions**: `ApiProvider` also supplies the save actions for a run file or the run archive: a download on the web, a native save dialog on the desktop

## Desktop transport

- **Addon**: the `Backend` class of the N-API addon (`packages/app-napi`) builds the router with `api_router` once and exposes `fetch(message, onReply)`. It runs each request through the router in process with `tower::ServiceExt::oneshot`, on a tokio runtime the addon owns, without a socket or an HTTP server, and returns a handle whose `abort()` stops the request. `saveRunFile` and `saveRunArchive` write an output file or the zipped run folder to a path. `just gen` generates the TypeScript declarations in `packages/app-napi/index.d.ts`
- **Port messages**: the envelope of a request is transport framing, defined in Rust in `packages/app-napi/src/port.rs` as the tagged unions `PortMessage` (`request` with method, URL, headers and an optional UTF-8 body; `abort`) and `PortReply` (`head` with status and headers; `chunk` with one body frame as a `Uint8Array`; `end`; `error`). napi-rs generates their TypeScript types and rejects a message with a missing or wrongly typed field. The bodies inside are HTTP bodies, validated by the generated client
- **Port fetch**: `createPortFetch` in `packages/app-desktop/src/port-fetch.ts` is the `fetch` of the desktop client. It sends a request as a `PortMessage` with only the path and query of its URL, and returns a `Response` whose body stream receives the chunks without decoding; aborting the request's signal sends `abort`. Requests made before the port connects wait for it. When the utility process stops, open bodies and pending requests fail with the reason, and the event streams reconnect when it restarts. The desktop client uses the page origin as base URL, like the web client: the packaged app serves its page from `app://treetime/` and the development build from the Vite server
- **Utility process**: the Electron main process starts the addon in a utility process and keeps windows, dialogs and process supervision. For each window, main creates a `MessageChannelMain` and gives one port to the utility process and the other, through the preload script, to the renderer. `packages/app-desktop/src/backend-host.ts` in the utility process passes every request message to `Backend.fetch` and every reply to the port, knows no routes, and aborts the open requests when the port closes. Requests and event streams travel between the renderer and the utility process without passing through main. A download is written by Rust straight to the path the user picks in a save dialog. When the utility process exits, main tells every window and answers pending saves with an error. It restarts the utility process unless it stopped five times within a minute
- **IPC checks**: main accepts IPC messages only from frames of the application, denies new windows, opens external web links in the browser, and blocks navigation away from the application

## Alternatives considered

- **A subset of settings per operation**, with request structs separate from the CLI config. Rejected: the app offers every CLI setting, and separate request structs repeat the fields and defaults of the CLI config and drift from them. The concern that `serde(flatten)` disables `deny_unknown_fields` does not apply, because the schema check runs before deserialization and rejects unknown keys at every level
- **One RPC endpoint** that accepts `{ operation, args }` for every operation, with a table of operations that both transports dispatch. Rejected: the web app must use the public REST API, and a second entry point next to the REST routes doubles the contract that outside clients see
- **An HTTP server or a local socket in the desktop app**. Rejected: the desktop app opens no network listener. Running the router through `oneshot` in the addon gives the same routing, extractors and error mapping without one; the measured cost is 0.02 to 0.03 ms per small request, and none on responses of 1.6 MB
- **WebSocket for realtime**. Rejected: axum's WebSocket upgrade needs a hyper connection and cannot run through `oneshot`, so the desktop app could not use it. SSE streams from the server and REST requests from the client cover both directions
- **utoipa for the OpenAPI document**. Rejected: utoipa does not compare the response type of its path annotation with the handler's return type, and it has its own schema derive next to `schemars::JsonSchema`. aide 0.15 depends on schemars 0.9, so the pinned build is a 0.16 pre-release (see [kb/issues/N-app-aide-pinned-to-prerelease.md](../issues/N-app-aide-pinned-to-prerelease.md))
- **The TanStack Query plugin of `@hey-api/openapi-ts`**. Rejected: its query keys are one flat object per operation, which cannot express "everything under run `abc`", so the server's stale paths could not select the cache entries to invalidate

## Implementation

- `packages/app-commands/src/command.rs`: command names, config preparation and the runner that returns the written output files
- `packages/app-commands/src/check_config.rs`, `packages/app-commands/src/run_config.rs`: `check-config` and `run-config`
- `packages/app-commands/src/job.rs`: job events, the terminal event and cancellation tokens
- `packages/app-commands/src/runs/`: run records, the run folder layout, event log, lifecycle and output files; `app_events.rs`: `AppEvent`, stale paths and the app event log
- `packages/app-commands/src/config/properties.rs`: path roles (`x-path`) and CLI flags (`x-cli-flag`) of the config settings, read from the schema
- `packages/app-commands/src/bridge/service.rs`, `packages/app-commands/src/bridge/error.rs`: `AppService`, the shared implementation of every operation, and `ErrorResponse`
- `packages/app-server/src/routes.rs`: `api_router`, the handlers and their registration
- `packages/app-server/src/api/`: extractors, responses and schema generation settings for aide
- `packages/app-server/src/openapi.rs`: config components, the setting catalog and the discriminators of tagged unions
- `packages/app-server/src/events.rs`, `packages/app-server/src/confine.rs`, `packages/app-server/src/error.rs`: the event streams, input path confinement and error statuses
- `packages/app-napi/src/exports.rs`, `packages/app-napi/src/backend.rs`, `packages/app-napi/src/port.rs`, `packages/app-napi/src/guard.rs`: the `Backend` addon class, the in-process router, the port messages, file saving and panic handling
- `packages/app-desktop/src/main.ts`, `packages/app-desktop/src/backend.ts`, `packages/app-desktop/src/backend-host.ts`, `packages/app-desktop/src/preload.ts`: the main process, the utility process, the relay and the preload script
- `packages/app-desktop/src/port-fetch.ts`: the `fetch` of the desktop client
- `packages/app-contracts/src/client.ts`, `packages/app-contracts/src/generated/`: the client factory, `ApiError`, resumable streams, and the generated SDK, types and zod schemas
- `packages/app-ui/src/api/`: keys, hooks, event handling and the API context of the UI
