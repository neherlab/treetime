# App clients send the full command config

The HTTP server and the desktop back end accept, for each of the six app commands (`timetree`, `optimize`, `prune`, `ancestral`, `clock`, `mugration`), the same config object that `treetime <command> --config` reads. Every setting the CLI offers is available to the web and desktop apps, and all three clients run a command through one runner in `packages/app-commands`.

## Behavior

- **Request**: a run is created with a `CreateRunRequest`: the command name, the command's config as JSON with the keys and values of `packages/schemas/input-config-<command>.schema.json`, an optional title, and `defer_start` to wait for uploads before the run starts. The OpenAPI document `packages/app-contracts/openapi.json` embeds the config schemas as `<Command>Config` components, and the TypeScript types and zod schemas in `packages/app-contracts/src/generated/` are generated from it
- **Validation**: the config goes through the CLI config loader: defaults are filled in, the schema check rejects unknown keys (nested ones included), wrong types and invalid enum values, and the conversion to run arguments rejects missing required inputs. Error messages are the ones the CLI prints for the same config file
- **Config check**: `check-config` takes a command name and a config as YAML or JSON text. It returns either the config with every default filled in, the equivalent command line and YAML config, and the pre-run checks, or the error message, its cause chain, each problem with its location in the text, and the checks
- **Run events**: every command runs as a run, a record on disk (`run.json`) with its own folder. A run emits `started`, then `progress`, `log` and iteration events, then exactly one `terminal` event, and every event is appended to the run's `events.jsonl`. The terminal event is `ok` with the output files that exist after the run and their kinds, `error` with the message and its cause chain, `cancelled`, or `interrupted` for a run that was still running when the process stopped. A rejected config, a failed command and a panic all end in an `error` terminal event. Clients subscribe from an event offset, so a reloaded page or a reopened app resumes a running run's stream
- **Cancellation**: each running run owns its cancellation token, keyed by run id. The server cancels a run on `POST /api/runs/{id}/cancel`; the desktop back end cancels through the `cancel-run` operation. Closing an event stream does not cancel the run. Cancelling one run leaves other runs running
- **Errors**: both transports report a failed operation as the same `ErrorResponse`: an error code (`not_found`, `upload_too_large`, `conflict`, `invalid_request`, `internal_error`), the message and its cause chain. The server answers each code with its own HTTP status. The addon catches every Rust panic and reports it as an `internal_error`, so a panic does not stop the desktop back end. The TypeScript bridge turns the response into a `BridgeError`
- **Paths on the server**: input paths must resolve, after following symbolic links, inside the data directory or the `inputs/` folder of a run (relative paths are resolved against the data directory). Browser files are uploaded into the run's own `inputs/` folder before the run starts. Output paths in the request are discarded; the server writes the outputs of a run to `<runs-dir>/<run-id>/out/`. Translation templates are expanded for each CDS and every expanded path is checked. The desktop back end reads any local path, because the desktop user owns the machine, and writes outputs into the run folder under `runs/` in the app's user-data directory

## Desktop transport

- **Operation table**: the `desktop_operations!` macro in `packages/app-commands/src/bridge/operations.rs` defines every request-response operation of the desktop back end once: its name, arguments and response type. It generates the `DesktopRequest` enum (a JSON object with `operation` and `args`), the `DesktopBackend` trait the addon implements, and the dispatch that returns the response as JSON text. `DesktopRequest` is part of the OpenAPI document, so the renderer builds requests with generated types and the back end rejects unknown operations and arguments
- **Addon**: the `Backend` class of the N-API addon (`packages/app-napi`) exposes `call(requestJson)` for the operations of the table, `subscribe(id, from, onEvent)` for the event stream of a run, returning a `Subscription` whose `unsubscribe()` stops the Rust event callback, and three file methods: `resolveRunFile`, `saveRunFile` and `saveRunArchive`. `just gen` generates its TypeScript declarations in `packages/app-napi/index.d.ts`
- **Utility process**: the Electron main process starts the addon in a utility process and keeps windows, dialogs and process supervision. For each window, main creates a `MessageChannelMain` and gives one port to the utility process and the other, through the preload script, to the renderer. Calls, event streams and file reads then travel between the renderer and the utility process without passing through main. A file read streams the file in chunks; a download is written by Rust straight to the path the user picks in a save dialog. When the utility process exits, main tells every window and answers pending saves with an error. It restarts the utility process unless it stopped five times within a minute
- **IPC checks**: main accepts IPC messages only from frames of the application, denies new windows, opens external web links in the browser, and blocks navigation away from the application

## Alternatives considered

- **A subset of settings per operation**, with request structs separate from the CLI config. Rejected: the app offers every CLI setting, and separate request structs repeat the fields and defaults of the CLI config and drift from them. The concern that `serde(flatten)` disables `deny_unknown_fields` does not apply, because the schema check runs before deserialization and rejects unknown keys at every level

## Implementation

- `packages/app-commands/src/command.rs`: command names, config preparation and the runner that returns the written output files
- `packages/app-commands/src/check_config.rs`, `packages/app-commands/src/run_config.rs`: `check-config` and `run-config`
- `packages/app-commands/src/job.rs`: job events, the terminal event and cancellation tokens
- `packages/app-commands/src/runs/`: run records, the run folder layout, event log, lifecycle and output files
- `packages/app-commands/src/config/properties.rs`: path roles (`x-path`) and CLI flags (`x-cli-flag`) of the config settings, read from the schema
- `packages/app-commands/src/bridge/operations.rs`, `packages/app-commands/src/bridge/error.rs`: the desktop operation table and `ErrorResponse`
- `packages/app-server/src/routes.rs`, `packages/app-server/src/events.rs`, `packages/app-server/src/confine.rs`, `packages/app-server/src/error.rs`: HTTP routes, the event stream, input path confinement and error statuses
- `packages/app-napi/src/exports.rs`, `packages/app-napi/src/backend.rs`, `packages/app-napi/src/guard.rs`, `packages/app-napi/src/subscription.rs`: the `Backend` addon class, the operation implementations, panic handling and event subscriptions
- `packages/app-desktop/src/main.ts`, `packages/app-desktop/src/backend.ts`, `packages/app-desktop/src/backend-host.ts`, `packages/app-desktop/src/preload.ts`: the main process, the utility process, the port protocol host and the preload bridge
- `packages/app-desktop/src/desktop-bridge.ts`, `packages/app-web/src/bridge-web.ts`: the desktop and web transports
- `packages/app-contracts/src/bridge.ts`: the TypeScript bridge that validates each response with the generated zod schemas, turns the terminal event into a result, a `CommandError`, or a `CancelledError`, and exposes runs
