# Grid point counts above 2^53 panic in debug builds

The grid constructors convert point counts and indices to floating point with `fn from_count()` ([packages/treetime-grid/src/grid.rs#L306-L308](../../packages/treetime-grid/src/grid.rs#L306-L308)), which calls `ToF64Exact::to_f64_exact()`. For `usize`, that conversion has a debug assertion that the value is at most $2^{53}$, the largest range in which every integer has an exact `f64` (`impl_to_f64_exact_bounded!`, [packages/treetime-utils/src/cast.rs#L20-L46](../../packages/treetime-utils/src/cast.rs#L20-L46)). A larger count therefore panics in a debug build instead of returning an error, and converts inexactly in a release build. For example, `Grid::from_range_n_points(0.0, 1.0, 9_007_199_254_740_994)` panics at the spacing computation ([packages/treetime-grid/src/grid.rs#L54](../../packages/treetime-grid/src/grid.rs#L54)), before any allocation.

`from_count()` is called in `Grid::from_range_n_points()` ([#L42-L78](../../packages/treetime-grid/src/grid.rs#L42-L78)), `Grid::from_start_dx()` ([#L80-L90](../../packages/treetime-grid/src/grid.rs#L80-L90)), `Grid::from_range_dx_anchored()` ([#L100-L115](../../packages/treetime-grid/src/grid.rs#L100-L115)), and `Grid::x_at()` ([#L245-L254](../../packages/treetime-grid/src/grid.rs#L245-L254)).

## Paths that can pass such a count

- **The grid point limit itself**: `MaxGridPoints::new()` accepts any value of at least 1000 and has no upper bound ([packages/treetime-grid/src/max_grid_points.rs#L22-L27](../../packages/treetime-grid/src/max_grid_points.rs#L22-L27)). `MaxGridPoints::point_count()` converts the limit with `to_f64_exact()` before it compares the required count ([#L42](../../packages/treetime-grid/src/max_grid_points.rs#L42)). A limit above $2^{53}$, for example `treetime timetree --max-grid-points 10000000000000000` or the same value in a config file, the desktop app settings, or `treetime-server --max-grid-points`, therefore reaches the assertion at the first grid of time inference in a debug build. Below that limit, every count that `point_count()` accepts is at most the limit and converts exactly. This path follows from the code; no debug run has shown it
- **Direct callers of the public grid API**: `Grid::from_range_n_points()` and `Grid::x_at()` are `pub` and take any `usize`. `x_at()` does not check that the index lies inside the grid. Inside the workspace, every call passes a count that `MaxGridPoints::point_count()` checked (`fn convolution_range_function()` in `packages/treetime-distribution/src/distribution_ops/convolve.rs`, `fn resample_to_mass_window()` in `packages/treetime-distribution/src/distribution_ops/mass_domain.rs`) or the length of an allocated array (`GridFn` constructors, the convolution result), which cannot exceed $2^{53}$ elements
- **Derived grids**: `Grid::shifted()`, `Grid::negated()`, `Grid::scaled()`, and `Grid::slice()` reuse the count of an existing grid, so they pass no count that a constructor did not already accept

## Fix direction

- Check the supported count range before the conversion, and return a contextual error that names the count and the grid range in every constructor that calls `from_count()`; let `x_at()` reject an index outside the grid, or make it private to the crate
- Bound `MaxGridPoints::new()` above at $2^{53}$ or a lower limit that a run can allocate, with a message that names the bound, so the CLI, the config schema, the app settings, and the server option reject such a limit before a run starts
- Add tests for a count of $2^{53} + 2$ in `Grid::from_range_n_points()` and for a limit above the bound in `MaxGridPoints::new()`, both asserting the error message
